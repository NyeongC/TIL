# CKAD 팁

### 시험장

* 문제 지시에 따라 SSH로 서버에 접속한다.
* `kubectl`, `k` 같은 단축어가 미리 설정되어 있을 수 있다.
* 문제에 나온 Namespace, 리소스명, 경로는 클릭해서 복사하면 오타를 줄일 수 있다.
* 문제의 주요 키워드를 누르면 Kubernetes 공식 문서로 이동할 수 있다.
* 긴 YAML 수정은 시험장의 VS Codium을 활용한다.

### 문제 풀이

#### Namespace 지정

`-n`의 위치는 앞이나 뒤 모두 가능하다.

```bash
k get pods -n alpha
k -n alpha get pods
```

둘 다 `alpha` Namespace의 Pod를 조회한다.

> `ns`는 Namespace 리소스 단축어이고, Namespace 지정 옵션은 `-n`이다.

```bash
k get ns
```

---

#### 공식 문서 YAML 복사 후 Namespace 넣기

공식 문서에서 YAML을 복사하면 Namespace가 없는 경우가 많다.

이때 `metadata` 아래에 `namespace`를 추가한다.

```yaml
metadata:
  name: sample-app
  namespace: alpha
```

파일 안에 Namespace를 넣었다면 다음처럼 적용해도 된다.

```bash
k apply -f sample-app.yaml
```

파일에 Namespace가 없다면 명령어에서 지정한다.

```bash
k apply -f sample-app.yaml -n alpha
```

#### 자주 사용하는 단축어

```text
po      Pods
deploy  Deployments
svc     Services
sa      ServiceAccounts
ns      Namespaces
cm      ConfigMaps
```

`k`는 `kubectl`의 Shell Alias다.

#### 실행 중인 리소스를 YAML로 확인

```bash
k get deploy sample-app -n alpha -o yaml
```

파일로 복사:

```bash
k get deploy sample-app -n alpha -o yaml > sample-app.yaml
```

복사한 YAML로 새 리소스를 만들 때는 이름, Label, Selector, 이미지 등을 수정한다.

---

#### `vi`와 `kubectl edit` 구분

새 YAML 파일을 만들거나 파일을 수정할 때는 `vi`를 사용한다.

```bash
vi sample-app.yaml
k apply -f sample-app.yaml
```

현재 클러스터에 실행 중인 리소스를 바로 수정할 때는 `kubectl edit`을 사용한다.

```bash
k edit deploy sample-app -n alpha
```

정리:

```text
vi             로컬 YAML 파일 수정 → apply 필요
kubectl edit   실행 중인 리소스 직접 수정 → 저장하면 바로 적용
```

시험에서는 새 리소스를 만들거나 복사해서 수정할 때 `vi`, 기존 리소스의 값을 빠르게 바꿀 때 `kubectl edit`이 편하다.

#### Blue-Green 배포

Blue와 Green Deployment는 서로 다른 Label을 사용한다.

```yaml
# Blue Pod
labels:
  app: sample-app
  color: blue
```

```yaml
# Green Pod
labels:
  app: sample-app
  color: green
```

Service가 Blue를 바라보는 상태:

```yaml
selector:
  app: sample-app
  color: blue
```

Green Deployment를 먼저 생성하고 Pod가 정상적으로 `Running`, `Ready` 상태인지 확인한다.

```bash
k get pods -n alpha
```

그다음 Service의 Selector만 Green으로 변경한다.

```yaml
selector:
  app: sample-app
  color: green
```

빠르게 변경:

```bash
k patch svc sample-service -n alpha \
  --type=merge \
  -p '{"spec":{"selector":{"app":"sample-app","color":"green"}}}'
```

Service는 별도로 재시작할 필요가 없다.

Selector를 변경하면 새로운 요청은 거의 즉시 Green Pod로 전달된다.

> Green Pod를 먼저 준비하고 Service Selector만 바꾸기 때문에 중단 없이 전환할 수 있다.

```text

```

`-f -`의 `-`는 표준입력을 의미한다.

## ㅠㅠ 실전 실패

### Script 안에서는 `k` Alias가 안 먹을 수 있음

터미널에서는 다음 명령이 실행될 수 있다.

```bash
k get pods -n alpha
```

하지만 `k`는 실제 실행 파일이 아니라 `kubectl`의 Alias이므로, Shell Script에서는 인식되지 않을 수 있다.

따라서 Script 안에서는 `kubectl`을 사용한다.

```bash
echo "kubectl get pods -n alpha -o custom-columns='NAME:.metadata.name,QOS:.status.qosClass'" \
> /opt/practice/qos-check.sh
```

다음 형태는 피하는 것이 안전하다.

```bash
echo "k get pods -n alpha -o custom-columns='NAME:.metadata.name,QOS:.status.qosClass'" \
> /opt/practice/qos-check.sh
```

#### CronJob 설정과 필드 위치

CronJob은 내부에 `Job` 설정과 `Pod` 설정이 중첩되어 있다.

```text
CronJob
└─ spec
   ├─ schedule
   ├─ failedJobsHistoryLimit
   ├─ successfulJobsHistoryLimit
   └─ jobTemplate
      └─ spec                     ← Job 설정
         ├─ completions
         ├─ backoffLimit
         ├─ activeDeadlineSeconds
         └─ template
            └─ spec               ← Pod 설정
               ├─ restartPolicy
               └─ containers
```

문제 조건과 실제 필드 위치:

```text
30분마다 실행             spec.schedule
실패한 Job 120개 보관      spec.failedJobsHistoryLimit
성공한 Job 2개 보관        spec.successfulJobsHistoryLimit
2번 성공해야 완료          spec.jobTemplate.spec.completions
실패 시 3번 재시도         spec.jobTemplate.spec.backoffLimit
30초가 지나면 Job 종료     spec.jobTemplate.spec.activeDeadlineSeconds
Pod를 재시작하지 않음      spec.jobTemplate.spec.template.spec.restartPolicy
```

전체 YAML:

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: sample-batch
  namespace: alpha
spec:
  schedule: "*/30 * * * *"
  failedJobsHistoryLimit: 120
  successfulJobsHistoryLimit: 2
  jobTemplate:
    spec:
      completions: 2
      backoffLimit: 3
      activeDeadlineSeconds: 30
      template:
        spec:
          restartPolicy: Never
          containers:
            - name: busybox
              image: busybox:stable
              command: ["sh", "-c", "date"]
```

CronJob 생성:

```bash
k apply -f sample-cronjob.yaml
```

CronJob을 기반으로 테스트용 Job 즉시 생성:

```bash
k create job sample-batch-test \
  --from=cronjob/sample-batch \
  -n alpha
```

결과 확인:

```bash
k get cronjob,job,pod -n alpha
```

#### 공식 문서에서 필드 위치 찾는 팁

공식 문서에서 기본 CronJob YAML을 복사한 뒤, 필드 위치가 기억나지 않으면 `kubectl explain`으로 확인한다.

CronJob 전체 구조 확인:

```bash
k explain cronjob.spec --recursive
```

Job 설정 확인:

```bash
k explain cronjob.spec.jobTemplate.spec
```

Pod 설정 확인:

```bash
k explain cronjob.spec.jobTemplate.spec.template.spec
```

특정 필드 위치와 설명 확인:

```bash
k explain cronjob.spec.failedJobsHistoryLimit
k explain cronjob.spec.jobTemplate.spec.backoffLimit
k explain cronjob.spec.jobTemplate.spec.activeDeadlineSeconds
```

정리:

```text
공식 문서에서 기본 YAML 복사
→ kubectl explain으로 필드 위치 확인
→ 문제에서 요구한 값 추가
→ apply 후 결과 확인
```

> `failedJobsHistoryLimit`, `successfulJobsHistoryLimit`는 CronJob 설정이다.  
> `completions`, `backoffLimit`, `activeDeadlineSeconds`는 Job 설정이다.  
> `restartPolicy`, `containers`는 Pod 설정이다.
