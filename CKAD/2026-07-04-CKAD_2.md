# CKAD 팁 2

## 1. Probe

### 개념

* `readinessProbe`: 요청을 받을 준비가 됐는지 확인
  실패하면 Service 대상에서 제외되지만 컨테이너를 재시작하지는 않는다.
* `livenessProbe`: 컨테이너가 살아 있는지 확인
  계속 실패하면 컨테이너를 재시작한다.

### Probe 추가 위치

`spec.template.spec.containers` 아래에 추가한다.

```yaml
containers:
  - name: httpd
    image: public.ecr.aws/docker/library/httpd:latest
    ports:
      - containerPort: 80

    # 컨테이너가 살아 있는지 확인
    livenessProbe:
      httpGet:
        path: /helathz   # 문제에 이렇게 나오면 오타 같아도 그대로 작성
        port: 80
      initialDelaySeconds: 5
      periodSeconds: 10
      failureThreshold: 3

    # 요청을 받을 준비가 됐는지 확인
    readinessProbe:
      httpGet:
        path: /readyz
        port: 80
      initialDelaySeconds: 2
      periodSeconds: 5
```

### 적용 확인

```bash
# Deployment 변경이 정상적으로 완료됐는지 확인
kubectl -n galaxy rollout status deploy/warp-core

# Probe가 실제로 들어갔는지 확인
kubectl -n galaxy describe deploy/warp-core

# Probe 실패 여부는 Pod의 Events에서 확인
kubectl -n galaxy describe pod <pod명>
```

`rollout status`에서는 다음 문구가 나오면 정상이다.

```text
successfully rolled out
```

`describe pod`에서는 맨 아래 `Events`에 아래 오류가 없는지 확인한다.

```text
Readiness probe failed
Liveness probe failed
Unhealthy
```

## 2. `리소스/이름`으로 외우기

명령어마다 띄어쓰기 방식 지원 여부가 다르므로 웬만하면 `/` 형식으로 통일한다.

```bash
kubectl logs deploy/warp-core -n galaxy
kubectl describe deploy/warp-core -n galaxy
kubectl edit deploy/warp-core -n galaxy
kubectl delete deploy/warp-core -n galaxy

kubectl rollout status deploy/warp-core -n galaxy
kubectl rollout history deploy/warp-core -n galaxy
kubectl rollout undo deploy/warp-core -n galaxy
```

`rollout status`는 아래 두 형식 모두 가능하다.

```bash
kubectl rollout status deploy warp-core -n galaxy
kubectl rollout status deploy/warp-core -n galaxy
```

하지만 다음은 보통 사용하지 않는다.

```bash
kubectl logs deploy warp-core -n galaxy
```

### Namespace의 주요 리소스 조회

```bash
kubectl get all -n <namespace>
```

`get all`은 주요 리소스를 한 번에 보여주지만 정말 모든 리소스를 보여주는 것은 아니다.

ConfigMap, Secret, Ingress, NetworkPolicy 등은 별도로 조회한다.

```bash
kubectl get cm,secret,ingress,networkpolicy -n <namespace>
```

## 3. ConfigMap + Secret + Pod

### 작업 순서

1. ConfigMap과 Secret 생성
2. Pod YAML 초안 생성
3. YAML에 `env` 추가
4. Pod 생성
5. 환경변수 확인

### ConfigMap과 Secret 생성

```bash
# ConfigMap 생성
kubectl -n apps create configmap app-config \
  --from-literal=database.url='postgres://db.example.com:5432/production'

# 일반 Secret은 반드시 generic이 들어간다!
kubectl -n apps create secret generic api-credentials \
  --from-literal=api.key='s3cr3t-ap1-k3y-f0r-pr0d'
```

암기:

```text
create configmap <이름>
create secret generic <이름>
```

### Pod YAML 초안 생성

```bash
kubectl -n apps run app-pod \
  --image=busybox:1.36 \
  --restart=Never \
  --command \
  --dry-run=client -o yaml \
  -- sh -c "sleep 3600" > pod.yaml
```

구조:

```text
kubectl run <Pod명> [kubectl 옵션] -- <컨테이너에서 실행할 명령>
```

각 부분의 의미:

```text
--command
뒤에 입력한 명령을 컨테이너의 실행 명령으로 사용

--dry-run=client -o yaml
실제 생성하지 않고 YAML만 출력

--
kubectl 옵션이 끝나고 컨테이너 명령이 시작됨

sh -c "sleep 3600"
컨테이너 안에서 실행할 실제 명령
```

### 순서 중요

아래처럼 `--dry-run`을 마지막 `--` 뒤에 쓰면 안 된다.

```bash
# 잘못된 순서
kubectl run app-pod \
  --image=busybox:1.36 \
  --command \
  -- sh -c "sleep 3600" \
  --dry-run=client -o yaml
```

마지막 `--` 뒤는 컨테이너 명령 영역이다.

안전하게 다음 순서로 외운다.

```bash
kubectl run app-pod \
  --image=busybox:1.36 \
  --command \
  --dry-run=client -o yaml \
  -- sh -c "sleep 3600" > pod.yaml
```

> `> pod.yaml`로 파일에 저장했기 때문에 터미널에 아무것도 안 뜨는 것이 정상이다.

```bash
cat pod.yaml
```

### 환경변수 추가

Pod YAML의 컨테이너 `image` 아래쪽에 `env`를 추가한다.

```yaml
containers:
  - name: app-pod
    image: busybox:1.36

    env:
      # ConfigMap의 database.url을 DATABASE_URL로 주입
      - name: DATABASE_URL
        valueFrom:
          configMapKeyRef:
            name: app-config
            key: database.url

      # Secret의 api.key를 API_KEY로 주입
      - name: API_KEY
        valueFrom:
          secretKeyRef:
            name: api-credentials
            key: api.key
```

공식 문서 검색어:

```text
configMapKeyRef
secretKeyRef
envFrom
Define Environment Variables for a Container
```

### 생성 및 확인

```bash
kubectl apply -f pod.yaml

kubectl -n apps get pod
kubectl -n apps describe pod/app-pod

# 환경변수 확인
kubectl -n apps exec pod/app-pod -- env
```

## 4. Deployment 업데이트와 롤백

이미지 변경은 `set image` 또는 `edit` 둘 다 가능하다.

```bash
# 이미지만 빠르게 변경
kubectl set image deploy/web1 <컨테이너명>=<이미지>

# 이미지 외에 strategy, probe 등도 같이 변경
kubectl edit deploy/web1
```

기본 순서:

```bash
# 변경 완료 확인
kubectl rollout status deploy/web1

# Revision 확인
kubectl rollout history deploy/web1

# 이전 버전으로 롤백
kubectl rollout undo deploy/web1

# 롤백 완료 확인
kubectl rollout status deploy/web1
```

롤백 문제의 채점 포인트가 이전 이미지로 돌아가는 것이라면 이미지가 복구됐는지만 확인하면 된다.

```bash
kubectl get deploy/web1 \
  -o jsonpath='{.spec.template.spec.containers[*].image}{"\n"}'
```

`rollout undo` 후 이미지가 이전 버전으로 돌아갔지만 Deployment의 `strategy`가 그대로일 수도 있다.

문제에서 이전 이미지로 롤백하라고 했다면 보통 상관없다.

## 5. Pod + Service + HTTP 테스트

### 서버 Pod 생성

```bash
# --labels의 s 주의
kubectl -n pluto run project-plt-6cc-api \
  --image=nginx:1.17.3-alpine \
  --labels=project=plt-6cc-api
```

Service의 `selector`와 Pod의 `label`이 일치해야 한다.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: project-plt-6cc-svc
  namespace: pluto
spec:
  selector:
    project: plt-6cc-api   # Pod의 label과 연결
  ports:
    - protocol: TCP
      port: 3333           # Service 포트
      targetPort: 80       # Pod 컨테이너 포트
```

```bash
kubectl apply -f service.yaml

# Endpoint가 보이면 Service와 Pod가 정상 연결된 것
kubectl -n pluto get endpoints project-plt-6cc-svc
```

### HTTP 요청용 임시 Pod

```bash
kubectl -n pluto run temp \
  --image=busybox:1.36 \
  --command -- sleep 3600
```

BusyBox를 사용하는 이유:

* 가볍고 빠르다.
* `wget`이 있어 HTTP 테스트에 편하다.
* `sleep 3600`은 Pod가 바로 종료되지 않게 한다.
* `1.36`은 반드시 외울 버전은 아니며 문제에서 지정하면 지정된 버전을 사용한다.

### Service 호출 결과 저장

```bash
kubectl -n pluto exec pod/temp -- \
  wget -qO- http://project-plt-6cc-svc:3333/ \
  > /opt/course/10/service_test.html
```

```text
-q   불필요한 출력 숨김
-O-  HTTP 응답 내용을 화면으로 출력
>    출력 내용을 Control Plane의 파일로 저장
```

확인:

```bash
cat /opt/course/10/service_test.html
```

### 로그 저장

```bash
kubectl -n pluto logs pod/project-plt-6cc-api \
  > /opt/course/10/service_test.log
```

## 6. Docker와 Buildx

### 일반 Docker

```bash
# 이미지 빌드
docker build -t myapp:2.1 .

# 로컬 이미지를 Docker TAR로 저장
docker save -o exports/myapp-v2.1.tar myapp:2.1
```

### Buildx

```bash
# 빌드하면서 바로 Docker TAR로 출력
docker buildx build \
  -t myapp:2.1 \
  -o type=docker,dest=exports/myapp-v2.1.tar \
  .
```

주의:

```text
docker buildx buildx  X
docker buildx build   O

mayapp  X
myapp   O
```

암기:

```text
docker save:
-o <파일> <이미지>

buildx:
-o type=docker,dest=<파일>
```

OCI 형식이면 `type=oci`를 사용한다.

```bash
docker buildx build \
  -t myapp:2.1 \
  -o type=oci,dest=exports/myapp-v2.1.tar \
  .
```

## 7. Ingress와 `/etc/hosts`

### Ingress란?

Host 또는 URL 경로에 따라 외부 HTTP 요청을 서로 다른 Service로 전달하는 리소스다.

```text
streams.local/api   → api-service
streams.local/video → video-service
```

### Ingress 생성

```bash
kubectl create ingress app-ingress \
  -n streaming \
  --class=traefik \
  --rule="streams.local/api*=api-service:80" \
  --rule="streams.local/video*=video-service:80"
```

의미:

```text
--class=traefik
Traefik Ingress Controller 사용

streams.local/api*
streams.local 호스트의 /api로 시작하는 요청

api-service:80
api-service의 80번 포트로 전달
```

생성 후 확인:

```bash
kubectl -n streaming get ingress app-ingress -o yaml
```

확인할 것:

```text
ingressClassName: traefik
pathType: Prefix
Service 이름과 포트
```

### Traefik이 실행 중인 Node 확인

```bash
kubectl get pods -A -o wide | grep -i traefik
```

출력의 `NODE` 열을 확인한다.

```text
traefik-xxxxx   1/1   Running   ...   node01
```

그다음 `node01`의 IP를 확인한다.

```bash
kubectl get node node01 -o wide
```

또는:

```bash
kubectl get nodes -o wide
```

보통 해당 Node의 `INTERNAL-IP`를 `/etc/hosts`에 등록한다.

Control Plane을 무조건 제외하는 것은 아니며, Traefik이 실행 중인 Node와 접근 가능한 IP를 기준으로 판단한다.

### `/etc/hosts` 등록

```bash
echo "172.30.2.2 streams.local" | sudo tee -a /etc/hosts
```

등록되는 내용:

```text
172.30.2.2 streams.local
```

```text
/etc/hosts
현재 컴퓨터에서만 사용하는 간단한 DNS 설정

tee
입력받은 내용을 파일에 기록

-a
기존 내용을 덮어쓰지 않고 마지막에 추가
```

## 8. NetworkPolicy

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: np-redis
  namespace: jupiter
spec:
  # app=redis Pod에 이 정책 적용
  podSelector:
    matchLabels:
      app: redis

  # 들어오는 통신과 나가는 통신 모두 제한
  policyTypes:
    - Ingress
    - Egress

  ingress:
    - from:
        # 같은 Namespace에서 app=app1 또는 app=app2인 Pod만 허용
        - podSelector:
            matchExpressions:
              - key: app
                operator: In
                values:
                  - app1
                  - app2
      ports:
        # Redis TCP 6379 포트만 허용
        - protocol: TCP
          port: 6379

  egress:
    # Redis Pod가 외부로 나갈 때 DNS 통신만 허용
    - ports:
        - protocol: UDP
          port: 53
        - protocol: TCP
          port: 53
```

적용:

```bash
kubectl apply -f - <<EOF
# YAML 내용
EOF
```

한 줄 정리:

```text
app=redis Pod를 격리한다.

같은 jupiter Namespace의
app=app1 또는 app=app2 Pod만
Redis TCP 6379 포트에 접근할 수 있다.

Redis Pod가 새롭게 외부로 나가는 통신은
TCP/UDP 53번 DNS 요청만 허용한다.
```

확인:

```bash
kubectl -n jupiter get networkpolicy
kubectl -n jupiter describe networkpolicy np-redis
```
