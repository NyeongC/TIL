# Kubernetes 정리: envFrom / Ingress / NetworkPolicy

## 1. envFrom

`envFrom`은 ConfigMap이나 Secret 안에 있는 key들을 **전부 환경변수로 주입**할 때 사용한다.

하나씩 지정할 때는 `env.valueFrom`을 쓰고,
전체를 한 번에 넣을 때는 `envFrom`을 쓴다.

```bash
kubectl create configmap special-config \
  --from-literal=APP_ENV=production \
  --from-literal=APP_PORT=8080

kubectl create secret generic special-secret \
  --from-literal=DB_USER=admin \
  --from-literal=DB_PASSWORD=1234
```

위처럼 만들었다고 해보자.

그러면 Pod는 이렇게 작성한다.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: dapi-test-pod
spec:
  containers:
  - name: test-container
    image: registry.k8s.io/busybox:1.27.2

    # 환경변수 전체 출력 후 컨테이너 종료
    command: ["/bin/sh", "-c", "env"]

    envFrom:
    - configMapRef:
        name: special-config     # ConfigMap의 모든 key를 환경변수로 주입

    - secretRef:
        name: special-secret     # Secret의 모든 key를 환경변수로 주입

  restartPolicy: Never           # env 찍고 끝나는 테스트용 Pod라 Never
```

Pod 내부에는 이렇게 환경변수가 만들어진다.

```text
APP_ENV=production
APP_PORT=8080
DB_USER=admin
DB_PASSWORD=1234
```

정리하면 이거다.

```text
envFrom = ConfigMap/Secret 전체 key를 환경변수로 넣는다
key 이름 = 환경변수 이름
value 값 = 환경변수 값
```

Secret은 Kubernetes 내부에서는 base64 형태로 저장되지만,
Pod 안에 환경변수로 들어올 때는 원래 값으로 들어온다.

확인할 때는 보통 이렇게 본다.

```bash
kubectl logs dapi-test-pod
```

# 2. Ingress란?

Ingress는 외부 HTTP/HTTPS 요청을 Kubernetes 내부 Service로 보내주는 라우터 역할이다.

흐름은 이렇게 보면 된다.

```text
외부 사용자
  ↓
Ingress
  ↓
Service
  ↓
Pod
```

중요한 건 Ingress가 Pod로 바로 보내는 게 아니라는 점이다.

```text
Ingress는 Service로 보낸다.
Service는 selector로 Pod를 찾는다.
Deployment는 Pod를 만들고 관리할 뿐이다.
```

즉 연결 관계는 이렇게 본다.

```text
Deployment
  └─ Pod 생성

Service
  └─ Pod label 보고 연결

Ingress
  └─ host/path 보고 Service로 연결
```

# 3. Ingress 기본 구조

Ingress에서 제일 헷갈리는 건 `-` 위치다.

`rules`는 리스트라서 `-`가 붙는다.
그런데 그 안의 `host`, `http`는 **같은 rule 한 덩어리의 속성**이다.

```yaml
rules:
- host: legacy.example.com   # rules 목록의 1번째 항목 시작
  http:                      # 같은 항목 안의 속성
```

이렇게 봐야 한다.

```text
rules:
- host
  http
```

그런데 아래처럼 쓰면 틀린다.

```yaml
rules:
- host: legacy.example.com
- http:
```

이렇게 쓰면 Kubernetes 입장에서는 아래처럼 해석한다.

```text
rules[0] = host만 있음
rules[1] = http만 있음
```

즉, `host`와 `http`가 서로 다른 rule이 돼버린다.

정답 구조는 이거다.

```text
rules[0] = host + http 같이 있음
```

암기 포인트는 이거다.

```text
rules 밑에 - 한 번
paths 밑에 - 한 번 또는 여러 번
```

# 4. Ingress rewrite

레거시 앱이 `/`만 처리하는데, 외부에서는 `/app`으로 접속하게 만들고 싶을 때 rewrite를 쓴다.

예를 들어 사용자는 이렇게 접속한다.

```text
legacy.example.com/app
```

그런데 백엔드 앱은 `/app`을 모른다.
`/`만 처리할 수 있다.

그래서 Ingress에서 경로를 바꿔준다.

```text
외부 요청: /app
백엔드 수신: /
```

NGINX Ingress에서는 아래 annotation을 사용한다.

```yaml
nginx.ingress.kubernetes.io/rewrite-target: /
```

CKAD 문제에서는 NGINX Ingress 기준으로 자주 나오니까,
rewrite 문제에서는 거의 통으로 외워도 된다.

```bash
kubectl apply -f - <<EOF
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: legacy-ingress
  namespace: legacy
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: / # /app으로 들어온 요청을 백엔드에는 / 로 전달
spec:
  rules:
  - host: legacy.example.com      # host와 http는 같은 rule 안에 있어야 함
    http:                         # 여기 앞에 - 붙이면 다른 rule이 돼서 틀림
      paths:
      - path: /app                # 외부에서 받을 path
        pathType: Prefix          # /app으로 시작하는 요청 매칭
        backend:
          service:
            name: legacy-svc      # Ingress는 Pod가 아니라 Service로 보냄
            port:
              number: 80          # Service의 port
EOF
```

정리하면:

```text
legacy.example.com/app 으로 들어오면
Ingress가 legacy-svc:80 으로 보내고
백엔드에는 / 로 바꿔서 전달한다.
```

# 5. ingressClassName: nginx

```yaml
spec:
  ingressClassName: nginx
```

이건 이 Ingress를 **어떤 Ingress Controller가 처리할지 지정**하는 값이다.

Ingress 자체는 그냥 규칙 문서에 가깝다.
실제로 외부 요청을 받아서 처리하는 건 Ingress Controller다.

```text
Ingress 리소스 = 규칙 문서
Ingress Controller = 실제 트래픽 처리 담당
```

그래서 이렇게 보면 된다.

```text
ingressClassName: nginx
= 이 Ingress는 nginx ingress controller가 처리해라
```

문제에서 아래처럼 말하면 넣어야 한다.

```text
Use ingressClassName nginx
```

또는 예시 YAML에 이미 아래가 있으면 그대로 살리는 게 좋다.

```yaml
ingressClassName: nginx
```

안 넣어도 동작하는 클러스터도 있지만,
시험에서는 문제에서 요구하면 그냥 넣는 게 맞다.

# 6. Ingress TLS

TLS는 HTTPS 처리할 때 쓴다.

```yaml
tls:
- hosts:
  - heroes.ua-academy.com
  secretName: ua-heroes-tls
```

뜻은 이거다.

```text
heroes.ua-academy.com 으로 HTTPS 요청이 오면
ua-heroes-tls Secret에 들어있는 인증서/키를 사용한다.
```

TLS Secret은 보통 문제에서 미리 만들어져 있다.

보통 Secret 안에는 아래 값이 들어있다.

```text
tls.crt
tls.key
```

여기서 중요한 점:

```text
tls.hosts의 도메인
rules.host의 도메인
인증서의 도메인

보통 이 셋이 맞아야 한다.
```

즉 `tls.hosts`는 그냥 아무거나 적는 게 아니라,
HTTPS 인증서를 적용할 도메인을 적는 곳이다.

---

# 7. HTTPS + path 2개 라우팅 예시

```bash
kubectl apply -f - <<EOF
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: hero-reg-ingress
  namespace: class-1a
spec:
  ingressClassName: nginx          # 이 Ingress는 nginx controller가 처리

  tls:
  - hosts:
    - heroes.ua-academy.com        # HTTPS 인증서 적용할 host, 아래 rules.host와 맞추는 게 기본
    secretName: ua-heroes-tls      # 미리 만들어진 TLS Secret

  rules:
  - host: heroes.ua-academy.com    # 이 도메인으로 들어온 요청만 처리
    http:                          # host와 같은 rule 안에 있어야 함, 두 번 쓰면 안 됨
      paths:                       # paths도 한 번만 쓰고, 아래에 path를 여러 개 둔다

      - path: /register            # /register 요청은 register-service로
        pathType: Prefix
        backend:
          service:
            name: register-service
            port:
              number: 80

      - path: /verify              # /verify 요청은 verify-service로
        pathType: Prefix
        backend:
          service:
            name: verify-service
            port:
              number: 80
EOF
```

이 구조에서 제일 중요한 건 이거다.

```text
host 하나
  http 하나
    paths 하나
      - path 여러 개
```

틀린 예시:

```yaml
rules:
- host: heroes.ua-academy.com
  http:
    paths:
    - path: /register
      ...
  http:
    paths:
    - path: /verify
      ...
```

`http:`를 두 번 쓰면 안 된다.

또 이것도 틀린다.

```yaml
http:
  paths:
  - path: /register
    ...
  paths:
  - path: /verify
    ...
```

`paths:`도 두 번 쓰면 안 된다.

정답은 이거다.

```yaml
rules:
- host: heroes.ua-academy.com
  http:
    paths:
    - path: /register
      ...
    - path: /verify
      ...
```

# 8. NetworkPolicy란?

NetworkPolicy는 Pod 간 통신을 제한하거나 허용하는 방화벽 규칙이다.

Ingress랑 헷갈리면 안 된다.

```text
Ingress
= 외부 HTTP/HTTPS 요청을 Service로 라우팅

NetworkPolicy
= Pod가 어디와 통신할 수 있는지 제어
```

NetworkPolicy 안에도 `Ingress`, `Egress`라는 말이 나오는데,
여기서의 Ingress는 `kind: Ingress`랑 다른 의미다.

```text
NetworkPolicy Ingress = 들어오는 트래픽 제어
NetworkPolicy Egress  = 나가는 트래픽 제어
```

# 9. 서로 다른 namespace로 Egress 허용하기

문제 상황:

```text
netpol-demo9 namespace의 source-pod가
external-ns namespace의 target-pod에게
TCP 80 포트로만 나가게 허용
```

즉 이렇게 정리된다.

```text
출발지 namespace: netpol-demo9
출발지 pod label: app=source

목적지 namespace: external-ns
목적지 pod label: app=target

허용 포트: TCP 80
방향: Egress
```

NetworkPolicy는 **출발지 Pod가 있는 namespace에 만든다.**

```yaml
metadata:
  namespace: netpol-demo9
```

그리고 `podSelector`는 이 정책을 적용받을 출발지 Pod를 고른다.

```yaml
podSelector:
  matchLabels:
    app: source
```

즉 이 뜻이다.

```text
netpol-demo9 namespace 안에서
app=source 라벨을 가진 Pod에게
이 Egress 정책을 적용한다.
```

# 10. Cross-Namespace Egress 정답 예시

```bash
kubectl apply -f - <<EOF
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: external-target
  namespace: netpol-demo9          # 정책은 출발지 Pod가 있는 namespace에 생성
spec:
  podSelector:
    matchLabels:
      app: source                  # 이 정책을 적용할 출발지 Pod 라벨

  policyTypes:
  - Egress                         # Engress 아님, Egress = 나가는 트래픽

  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: external-ns # namespace 이름으로 목적지 namespace 선택

      podSelector:                 # 여기 앞에 - 붙이면 안 됨, 위 namespaceSelector와 같은 목적지 조건
        matchLabels:
          app: target              # 목적지 Pod 라벨

    ports:
    - protocol: TCP
      port: 80                     # 목적지 Pod/Service 쪽에서 허용할 포트
EOF
```

여기서 중요한 구조는 이거다.

```yaml
to:
- namespaceSelector:
    ...
  podSelector:
    ...
```

`namespaceSelector`와 `podSelector`는 같은 `to` 항목 안에 있어야 한다.

즉 의미는 이거다.

```text
external-ns namespace 안에 있는
app=target Pod로 가는 트래픽만 허용
```

만약 이렇게 쓰면 의미가 달라지거나 틀릴 수 있다.

```yaml
to:
- namespaceSelector:
    ...
- podSelector:
    ...
```

이건 아래처럼 두 개의 목적지를 따로 적은 꼴이다.

```text
목적지 1 = namespace 조건만 있음
목적지 2 = pod 조건만 있음
```

그래서 이 문제에서는 `podSelector` 앞에 `-`를 붙이면 안 된다.

# 11. namespaceSelector 주의

NetworkPolicy에서 목적지 namespace를 아래처럼 직접 쓰는 문법은 없다.

```yaml
namespace: external-ns
```

이건 틀린 방식이다.

NetworkPolicy의 `namespaceSelector`는 namespace의 label을 보고 선택한다.

namespace 이름으로 선택할 때는 보통 아래 라벨을 사용한다.

```yaml
namespaceSelector:
  matchLabels:
    kubernetes.io/metadata.name: external-ns
```

CKAD에서는 이 형태로 외우면 된다.

```yaml
namespaceSelector:
  matchLabels:
    kubernetes.io/metadata.name: 네임스페이스명
```

# 12. 최종 암기 포인트

```text
envFrom
= ConfigMap/Secret의 모든 key를 환경변수로 주입

envFrom.configMapRef.name
= 가져올 ConfigMap 이름

envFrom.secretRef.name
= 가져올 Secret 이름

Ingress
= 외부 HTTP/HTTPS 요청을 Service로 라우팅

Ingress는 Pod가 아니라 Service로 보낸다

rules 밑에 - 한 번
paths 밑에 - 한 번 또는 여러 번

host와 http는 같은 rule 안에 있어야 한다

http 하나
paths 하나
path 여러 개

rewrite-target
= 외부 path를 백엔드가 받을 path로 바꿔주는 설정

nginx.ingress.kubernetes.io/rewrite-target: /
= NGINX Ingress에서 rewrite할 때 자주 쓰는 annotation

ingressClassName: nginx
= nginx ingress controller가 이 Ingress를 처리하게 지정

tls.hosts
= HTTPS 인증서를 적용할 도메인

tls.secretName
= tls.crt, tls.key가 들어있는 Secret 이름

NetworkPolicy
= Pod 통신 방화벽

Egress
= 나가는 트래픽 제어

metadata.namespace
= NetworkPolicy를 만들 위치, 보통 출발지 namespace

podSelector
= 정책을 적용할 출발지 Pod 선택

namespaceSelector
= 목적지 namespace를 label로 선택

kubernetes.io/metadata.name: 네임스페이스명
= namespace 이름으로 namespaceSelector 잡을 때 자주 쓰는 형태

NetworkPolicy의 to 안에서
namespaceSelector와 podSelector를 같이 쓰면
해당 namespace 안의 해당 pod만 목적지가 된다
```
