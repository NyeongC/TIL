# CKAD 추가 정리

## 1. Secret 사용 방법

Secret은 크게 두 가지 방식으로 사용한다.

```text
환경변수 주입 → env.valueFrom.secretKeyRef
파일로 마운트 → volumeMounts + volumes.secret.secretName
```

시험에서 둘 다 나올 수 있으므로 **두 방법 모두 알아야 한다.**

### 환경변수 + 파일 마운트

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: secret-handler
  namespace: moon
spec:
  containers:
  - name: app
    image: busybox:1.37.0
    command: ["/bin/sh", "-c", "sleep 1d"]

    # secret1의 값을 환경변수로 주입
    env:
    - name: SECRET1_USER
      valueFrom:
        secretKeyRef:
          name: secret1
          key: user
    - name: SECRET1_PASS
      valueFrom:
        secretKeyRef:
          name: secret1
          key: pass

    # secret2를 파일로 마운트
    volumeMounts:
    - name: secret2-vol
      mountPath: /tmp/secret2
      readOnly: true

  volumes:
  - name: secret2-vol
    secret:
      secretName: secret2
```

마운트되면 Secret의 각 key가 파일이 된다.

```text
/tmp/secret2/username
/tmp/secret2/password
```

기존 Pod는 대부분의 설정을 직접 수정할 수 없다.

```bash
# 원본 YAML 복사
cp /opt/course/14/secret-handler.yaml \
   /opt/course/14/secret-handler-new.yaml

# 기존 Pod 삭제 후 수정한 YAML로 재생성
kubectl delete pod secret-handler -n moon
kubectl apply -f /opt/course/14/secret-handler-new.yaml
```

`cp`는 파일이나 디렉터리를 복사하는 리눅스 명령어이다.

## 2. 사이드카 컨테이너

사이드카는 메인 컨테이너 옆에서 보조 작업을 수행하는 컨테이너이다.

예시 작업:

```text
로그 수집
프록시
설정 갱신
모니터링
```

### 로그 수집 사이드카 예제

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 1
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
    spec:
      containers:
      # 메인 컨테이너
      - name: myapp
        image: alpine:latest
        command:
        - sh
        - -c
        - |
          while true; do
            echo "logging" >> /opt/logs.txt
            sleep 1
          done
        volumeMounts:
        - name: data
          mountPath: /opt

      initContainers:
      # restartPolicy: Always를 사용하면
      # 초기화 후 종료되지 않고 사이드카로 계속 실행된다.
      - name: logshipper
        image: alpine:latest
        restartPolicy: Always
        command:
        - sh
        - -c
        - tail -F /opt/logs.txt
        volumeMounts:
        - name: data
          mountPath: /opt

      # 두 컨테이너가 로그 파일을 공유하기 위한 볼륨
      volumes:
      - name: data
        emptyDir: {}
```

핵심 연결 관계:

```text
메인 컨테이너 /opt
        ↕
emptyDir 볼륨
        ↕
사이드카 /opt
```

`volumeMounts.name`과 `volumes.name`은 반드시 같아야 한다.

## 3. 카나리 배포 20%

기존 Pod가 5개라면 다음과 같이 구성한다.

```text
기존 버전 4개
신규 버전 1개
전체 5개 중 신규 1개 → 약 20%
```

### 기존 Deployment 축소

```bash
kubectl scale deployment frontend --replicas=4
```

### 신규 Canary Deployment 생성

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend-canary
  namespace: default
spec:
  replicas: 1

  selector:
    matchLabels:
      app: frontend
      version: v2

  template:
    metadata:
      labels:
        app: frontend
        version: v2
    spec:
      containers:
      - name: nginx
        image: nginx:1.20
        ports:
        - containerPort: 80
```

기존 Service는 수정하지 않는다.

Service가 아래처럼 공통 라벨만 선택해야 한다.

```yaml
selector:
  app: frontend
```

그러면 기존 Pod와 Canary Pod가 모두 Service에 연결된다.

```text
Service selector → app: frontend
기존 Pod          → app: frontend
Canary Pod        → app: frontend, version: v2
```

`version: v2`는 Canary Deployment 내부 구분용이다.

## 4. SecurityContext

SecurityContext는 보안 관련 실행 옵션이다.

설정 위치는 두 가지가 있다.

```text
Pod 전체 설정       → spec.securityContext
특정 컨테이너 설정 → spec.containers[].securityContext
```

문제에서 **container-level securityContext**라고 하면 컨테이너 안에 작성한다.

```yaml
spec:
  containers:
  - name: joker-container
    image: public.ecr.aws/docker/library/busybox:latest

    securityContext:
      # 컨테이너가 실행 중 더 높은 권한을 얻지 못하게 설정
      allowPrivilegeEscalation: false

      # UID 3000 사용자로 프로세스 실행
      runAsUser: 3000

      # 컨테이너에 추가 Linux 권한 부여
      capabilities:
        add:
        - NET_BIND_SERVICE
        - NET_RAW
        - NET_ADMIN
```

주요 설정:

```yaml
securityContext:
  allowPrivilegeEscalation: false  # 실행 중 권한 상승 금지
  privileged: false                # 특권 컨테이너 사용 금지
  runAsUser: 3000                  # UID 3000으로 실행
  runAsNonRoot: true               # root 사용자 실행 금지
  readOnlyRootFilesystem: true     # 루트 파일시스템 쓰기 금지
```

`capabilities.add`는 컨테이너에 특정 Linux 권한을 추가한다.

```text
NET_BIND_SERVICE → 낮은 포트 사용 권한
NET_RAW          → Raw Socket 사용 권한
NET_ADMIN        → 네트워크 설정 변경 권한
```

시험에서는 문제에서 요구한 항목만 추가한다.

## 5. ConfigMap 파일 마운트와 ReadinessProbe

### ConfigMap 생성

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
  namespace: apps
data:
  APP_MODE: "production"
  APP_PORT: "8080"
```

ConfigMap의 `data` 값은 문자열이다.

숫자처럼 보이는 값은 YAML에서 숫자로 해석될 수 있으므로 따옴표를 사용하는 것이 안전하다.

### ConfigMap 마운트

```yaml
volumeMounts:
- name: foo
  mountPath: /etc/appconfig
  readOnly: true

volumes:
- name: foo
  configMap:
    name: app-config
```

마운트되면 key가 파일 이름이 된다.

```text
/etc/appconfig/APP_MODE → production
/etc/appconfig/APP_PORT → 8080
```

### ReadinessProbe

```yaml
readinessProbe:
  exec:
    command:
    - /bin/sh
    - -c
    - 'grep -qx "production" /etc/appconfig/APP_MODE && grep -qx "8080" /etc/appconfig/APP_PORT'
```

명령어 의미:

```text
/bin/sh -c
→ 뒤에 작성한 문자열을 셸 명령어로 실행

grep -q
→ 결과를 화면에 출력하지 않고 성공 여부만 반환

grep -x
→ 한 줄 전체가 정확히 일치하는지 확인

&&
→ 앞 명령어가 성공했을 때만 뒤 명령어 실행
```

즉 다음 두 조건을 모두 확인한다.

```text
APP_MODE 파일 내용가 production인지
APP_PORT 파일 내용이 8080인지
```

둘 다 일치하면 Probe 성공이다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app-workload
  namespace: apps
spec:
  replicas: 2
  selector:
    matchLabels:
      app: app-workload
  template:
    metadata:
      labels:
        app: app-workload
    spec:
      containers:
      - name: nginx
        image: nginx

        readinessProbe:
          exec:
            command:
            - /bin/sh
            - -c
            - 'grep -qx "production" /etc/appconfig/APP_MODE && grep -qx "8080" /etc/appconfig/APP_PORT'

        volumeMounts:
        - name: foo
          mountPath: /etc/appconfig
          readOnly: true

      volumes:
      - name: foo
        configMap:
          name: app-config
```

## 6. ServiceAccount

ServiceAccount는 **Pod가 Kubernetes API에 접근할 때 사용하는 계정**이다.

예시:

```text
Secret 조회
ConfigMap 조회
Pod 목록 조회
Kubernetes API 호출
```

사람이 사용하는 계정이 아니라 Pod가 사용하는 계정이다.

### Deployment에 ServiceAccount 지정

설정 위치:

```text
spec.template.spec.serviceAccountName
```

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
  namespace: payment
spec:
  template:
    spec:
      serviceAccountName: payment-sa

      containers:
      - name: payment-api
        image: nginx:1.25.3
```

Deployment의 최상위 `spec`가 아니라 **Pod 템플릿의 spec 안에 작성한다.**

```text
Deployment
└─ spec
   └─ template
      └─ spec
         └─ serviceAccountName
```

### serviceAccount와 serviceAccountName 차이

```yaml
serviceAccount: default
serviceAccountName: payment-sa
```

둘은 사실상 같은 역할을 하지만 다음 차이가 있다.

```text
serviceAccount     → 과거 필드, Deprecated
serviceAccountName → 현재 사용하는 공식 필드
```

시험에서는 `serviceAccountName`만 사용하면 된다.

두 필드를 서로 다른 값으로 동시에 설정하지 않는다.

### 적용 확인

```bash
kubectl get pods -n payment
```

```bash
kubectl get pod <새로-생성된-Pod> \
  -n payment \
  -o jsonpath='{.spec.serviceAccountName}'
```

결과:

```text
payment-sa
```
