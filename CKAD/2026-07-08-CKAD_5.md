# CKAD 추가 정리

## 1. Deployment 일시정지 후 변경

```bash
kubectl rollout pause deployment/api-server
```

Deployment를 일시정지하면 다음 값이 설정된다.

```yaml
spec:
  paused: true
```

- 이미지 등 `spec.template` 변경은 저장되지만 새로운 롤아웃은 시작되지 않는다.
- `replicas` 변경은 일시정지 상태에서도 반영될 수 있다.
- 변경을 모두 끝낸 뒤 `resume`하면 보류된 내용이 배포된다.

```bash
kubectl rollout resume deployment/api-server
kubectl rollout status deployment/api-server
```

## 2. Service selector

Service의 `spec.selector`는 **Pod의 라벨**을 찾는다.

```yaml
# Deployment
spec:
  selector:
    matchLabels:
      app: ecommerce-frontend
  template:
    metadata:
      labels:
        app: ecommerce-frontend   # Service가 찾는 Pod 라벨
```

```yaml
# Service
spec:
  selector:
    app: ecommerce-frontend       # Pod 라벨과 일치해야 함
```

> Service의 `metadata.labels`는 Service 자체의 라벨이다.  
> 실제 Pod 연결에는 `spec.selector`가 중요하다.

## 3. NodePort Service

```yaml
apiVersion: v1
kind: Service
metadata:
  name: ecommerce-frontend-service
  namespace: ecommerce-platform
spec:
  type: NodePort
  selector:
    app: ecommerce-frontend       # 연결할 Pod 라벨
  ports:
  - protocol: TCP
    port: 8000                    # Service가 클러스터 내부에서 받는 포트
    targetPort: 80                # 컨테이너가 실제로 사용하는 포트
    # nodePort: 30080             # 외부 접속 포트, 생략하면 자동 지정
```

접속 흐름:

```text
외부 사용자
→ NodeIP:nodePort
→ Service port
→ Pod targetPort
```

예시:

```text
NodeIP:30080 → Service:8000 → Container:80
```

`nodePort`를 생략하면 Kubernetes가 일반적으로 `30000~32767` 범위에서 자동 지정한다.

```bash
kubectl -n ecommerce-platform get svc ecommerce-frontend-service
```

## 4. exec 방식 Readiness Probe

명령어가 성공하면 Pod가 요청을 받을 준비가 된 것으로 판단한다.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: pod6
spec:
  containers:
  - name: busybox
    image: busybox:1.31.0

    # ready 파일을 만든 뒤 컨테이너 유지
    command: ["/bin/sh", "-c", "touch /tmp/ready && sleep 1d"]

    readinessProbe:
      exec:
        command:
        - /bin/sh
        - -c
        - cat /tmp/ready
      initialDelaySeconds: 5      # 컨테이너 시작 후 5초 뒤 검사
      periodSeconds: 10           # 10초마다 검사
```

- 명령어 종료 코드 `0`: 성공
- 종료 코드가 `0`이 아님: 준비되지 않음

## 6. ConfigMap 사용 방법

### 환경변수로 사용

```yaml
env:
- name: APP_MODE
  valueFrom:
    configMapKeyRef:
      name: app-config
      key: APP_MODE
```

### 파일로 마운트

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web-pod
spec:
  containers:
  - name: test-container
    image: nginx:1.29.0
    volumeMounts:
    - name: config                    # volumes.name과 일치
      mountPath: /usr/share/nginx/html

  volumes:
  - name: config                      # volumeMounts.name과 일치
    configMap:
      name: html-config               # 실제 ConfigMap 이름
```

연결 구조:

```text
ConfigMap html-config
→ Pod Volume config
→ /usr/share/nginx/html
```

ConfigMap의 각 key는 파일이 된다.

```text
index.html → /usr/share/nginx/html/index.html
error.html → /usr/share/nginx/html/error.html
```

## 7. ResourceQuota

ResourceQuota는 **네임스페이스 전체에서 사용할 수 있는 자원의 총량**을 제한한다.

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: app-quota
  namespace: production-apps
spec:
  hard:
    pods: "4"                    # 최대 Pod 수
    requests.cpu: "2000m"       # 전체 CPU request 합계
    requests.memory: "4Gi"      # 전체 Memory request 합계
    limits.cpu: "4000m"         # 전체 CPU limit 합계
    limits.memory: "8Gi"        # 전체 Memory limit 합계
```

컨테이너 자원 설정:

```yaml
resources:
  requests:
    cpu: "200m"                 # 최소 보장 요청량
    memory: "256Mi"
  limits:
    cpu: "500m"                 # 최대 사용 가능량
    memory: "512Mi"
```

```text
ResourceQuota = 네임스페이스 전체 총량 제한
```

## 8. LimitRange

LimitRange는 네임스페이스 안의 **개별 Container 또는 Pod 자원값**에 기본값과 범위를 설정한다.

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: mem-limit-range
  namespace: team-a
spec:
  limits:
  - type: Container
    default:
      memory: "256Mi"           # limit 미지정 시 자동 적용
    defaultRequest:
      memory: "128Mi"           # request 미지정 시 자동 적용
    max:
      memory: "512Mi"           # 허용되는 최대값
    min:
      memory: "64Mi"            # 허용되는 최소값
```

```text
ResourceQuota = 네임스페이스 전체 총량
LimitRange    = 개별 Container/Pod의 기본값·최소값·최대값
```

BusyBox는 가벼워서 종료되는 것이 아니라, **실행할 메인 프로세스가 끝나면 컨테이너도 종료**된다.

```yaml
command: ["sh", "-c", "sleep 1d"]
```

테스트할 때 컨테이너를 계속 실행시키기 위해 `sleep`을 사용한다.

## 9. API Resource와 API Version 확인

```bash
kubectl api-resources
```

클러스터에서 사용할 수 있는 리소스와 API Version을 확인한다.

```bash
kubectl api-resources | grep -i deployment
```

출력 예시:

```text
deployments   deploy   apps/v1   true   Deployment
```

즉 Deployment의 API Version은 다음과 같다.

```yaml
apiVersion: apps/v1
kind: Deployment
```

추가 명령어:

```bash
kubectl api-versions             # 지원되는 API Version 목록
kubectl explain deployment       # Deployment 구조 확인
kubectl explain deployment.spec  # spec 하위 필드 확인
```

## 10. Pod 네임스페이스 이동

Pod의 네임스페이스는 직접 변경할 수 없으므로, YAML을 추출한 뒤 다른 네임스페이스에 새로 생성한다.

```bash
# 기존 Pod YAML 추출
kubectl -n prime get pod web-app-04 -o yaml > pod.yml

# YAML 수정
vi pod.yml
```

YAML에서 다음 항목을 정리한다.

```yaml
metadata:
  namespace: mars

# 아래 자동 생성 항목은 삭제
# uid
# resourceVersion
# creationTimestamp
# managedFields
# ownerReferences
# status 전체
```

새 네임스페이스에 생성하고 확인한다.

```bash
kubectl apply -f pod.yml
kubectl -n mars get pod web-app-04
```

정상 실행을 확인한 뒤 기존 Pod를 삭제한다.

```bash
kubectl -n prime delete pod web-app-04
```

## 11. CronJob과 Job

```text
CronJob → 정해진 시간마다 Job 생성 → Job이 Pod 실행
```

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: db-backup
  namespace: payment
spec:
  schedule: "*/10 * * * *"        # 10분마다 실행
  successfulJobsHistoryLimit: 3   # 성공한 Job 3개 보관
  failedJobsHistoryLimit: 1       # 실패한 Job 1개 보관
  startingDeadlineSeconds: 100    # 실행 시간을 놓쳤을 때 100초까지 허용

  jobTemplate:
    spec:
      template:
        spec:
          containers:
          - name: backup
            image: busybox
            imagePullPolicy: IfNotPresent
            command:
            - /bin/sh
            - -c
            - 'date; echo "Starting backup"'

          restartPolicy: OnFailure
```

```bash
kubectl apply -f cronjob.yaml
```

CronJob을 기다리지 않고 즉시 한 번 실행하려면 Job을 생성한다.

```bash
kubectl create job manual-db-backup \
  --from=cronjob/db-backup \
  -n payment
```

```text
db-backup         = 반복 실행할 CronJob
manual-db-backup  = CronJob 설정을 복사한 1회성 Job
```

확인:

```bash
kubectl -n payment get cronjob
kubectl -n payment get job
kubectl -n payment get pod
```

## 12. echo와 cat

```bash
echo "hello"
```

- 문자열이나 변수 값을 출력한다.

```bash
cat file.txt
```

- 파일 내용을 출력한다.

```bash
kubectl apply -f - <<EOF
...
EOF
```

- `-f -`는 YAML을 파일이 아닌 표준 입력으로 받는다는 뜻이다.
- 아래 두 방식은 결과가 같다.

```bash
kubectl apply -f - <<EOF
...
EOF
```

```bash
cat <<EOF | kubectl apply -f -
...
EOF
```
