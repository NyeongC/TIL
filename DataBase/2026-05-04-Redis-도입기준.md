## Redis 도입 기준

### 1. 전체 판단 흐름

Redis 도입은 감으로 결정하지 않는다.

1. APM에서 호출 많은 API 확인
2. API 상세에서 병목 위치 확인
3. SQL 실행 패턴 확인
4. 바인드 변수 반복 여부 확인
5. 데이터 변경 빈도 확인
6. DB 최적화 여부 확인
7. 최종적으로 Redis 적용 여부 판단

---

### 2. 상세 시나리오

#### 1. APM에서 호출 많은 API 확인

- 호출 수 (TPS)
- 평균 응답 시간
- P95 응답 시간

예:
```
/menu/list
호출 수: 50,000회/일
평균 응답: 120ms
P95: 300ms
```

→ 캐시 후보 API 선정

---

#### 2. API 상세에서 병목 위치 확인

```
전체 응답: 120ms
DB 시간: 90ms
```

- DB 시간이 크면 → DB 병목 → 캐시 후보
- DB 시간이 작으면 → 다른 원인 탐색 (네트워크, 애플리케이션 로직 등)

---

#### 3. SQL 패턴 확인 (Oracle v$sql)

확인 항목:

- `executions` : 실행 횟수
- `cpu_time` : CPU 사용량
- `buffer_gets` : 메모리에서 읽은 블록 수
- `disk_reads` : 실제 디스크에서 읽은 블록 수
- 실행계획 및 인덱스 사용 여부

**실제 디스크 IO 확인 쿼리:**
```sql
SELECT
  sql_id,
  executions,
  disk_reads,
  buffer_gets,
  round(disk_reads / nullif(executions, 0)) AS disk_reads_per_exec,
  round(buffer_gets / nullif(executions, 0)) AS buffer_gets_per_exec
FROM v$sql
WHERE sql_text LIKE '%테이블명%'
ORDER BY last_active_time DESC;
```

- `disk_reads_per_exec`가 0에 가까우면 → 오라클 버퍼 캐시가 이미 메모리에서 처리 중
- 이 경우 Redis 도입 효과는 크지 않고, 오라클 커넥션 절약 목적 정도

**버퍼 캐시 히트율 확인:**
```sql
SELECT
  round(1 - (phy.value / (cur.value + con.value)), 4) * 100 AS buffer_hit_ratio
FROM v$sysstat phy, v$sysstat cur, v$sysstat con
WHERE phy.name = 'physical reads'
  AND cur.name = 'db block gets'
  AND con.name = 'consistent gets';
```

- 90% 이상이면 대부분 메모리에서 처리 중

---

#### 4. 바인드 변수와 쿼리 중복 감지 문제

오라클은 SQL 텍스트가 완전히 동일해야 같은 쿼리로 인식한다.
바인드 변수 없이 리터럴을 직접 넣으면 v$sql에서 각각 다른 sql_id로 잡혀 반복 여부 파악이 어렵다.

```sql
-- 오라클 입장에서 전부 다른 쿼리로 인식
SELECT * FROM messages WHERE user_id = 1001
SELECT * FROM messages WHERE user_id = 1002
```

**이럴 때는 force_matching_signature로 묶어서 확인:**
```sql
SELECT
  force_matching_signature,
  count(*) AS variants,
  sum(executions) AS total_exec,
  min(sql_text) AS sample_sql
FROM v$sql
WHERE sql_text LIKE '%테이블명%'
  AND force_matching_signature != 0
GROUP BY force_matching_signature
ORDER BY total_exec DESC;
```

- `force_matching_signature`가 같으면 리터럴만 다른 사실상 동일한 쿼리
- `total_exec`가 높으면 캐시 후보

**캐시 효율이 높은 조건 예시:**
```
-- 모든 유저가 공통으로 보는 데이터 (조건 고정)
EVENT_DATE = 오늘
COMPANY_CODE = A001
```

**캐시 효율이 낮은 조건 예시:**
```
-- 유저마다 다른 결과 (캐시 키가 무한히 늘어남)
USER_ID = 1001
USER_ID = 1002
```

---

#### 5. 데이터 변경 빈도

캐시 적합:
- 메뉴, 권한, 코드성 데이터
- 공지사항, 이벤트
- 배치 집계 데이터

캐시 부적합:
- 주문 상태
- 운송장 상태
- 재고
- 결제

---

#### 6. DB 최적화 여부

캐시 전에 먼저 확인:
- 인덱스 누락 여부
- 풀스캔 발생 여부
- 조인 구조
- 통계정보 최신화 여부

DB 자체 문제라면 캐시가 아니라 쿼리 튜닝이 먼저다.

---

### 3. Redis 도입 기준

#### ❌ 사용하지 않는 경우

- 쿼리가 이미 충분히 빠름
- PK 단건 조회
- 데이터가 자주 변경됨
- 유저마다 조건이 달라 캐시 키가 무한히 늘어남

---

#### ✅ 사용 가능한 경우

- 호출 횟수가 많음
- 동일한 결과가 반복됨
- 데이터 변경이 적음
- DB 부하가 실제로 있음
- 여러 서버간 공유가 필요함
- 트래픽이 적더라도 오라클 커넥션 절약이 필요한 경우

---

### 4. 핵심 정리

- 느리다고 캐시를 쓰는 것이 아니다
- 반복될 때 캐시를 쓴다
- 캐시 전에 쿼리 튜닝이 먼저다
- 디스크 IO가 낮아도 커넥션 절약 목적으로 캐시를 쓸 수 있다

---

### 5. 한 줄 핵심

API 반복 → SQL 반복 → 결과 동일 → 변경 적음 → DB 부담 확인 → 그때 Redis
