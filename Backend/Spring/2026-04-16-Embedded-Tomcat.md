## Embedded Tomcat과 배포 방식의 변화

```text
내장 톰캣 이란?

내장 톰캣은 Spring Boot 안에 Tomcat 웹 서버가 포함되어 있어, 별도의 WAS(Web Application Server)를 설치하거나 WAR 파일을 배포할 필요 없이 java -jar 명령 하나로 서버를 실행할 수 있게 해주는 기능입니다. 
```

### 과거 방식 (왜 불편했나)

과거 Spring 기반 웹 애플리케이션은 다음과 같은 방식으로 배포했다.

1. Tomcat(WAS)을 서버에 직접 설치
2. 프로젝트를 WAR 파일로 빌드
3. Tomcat의 `webapps` 폴더에 WAR 파일 배포
4. Tomcat 재시작

-> 문제점

* 서버마다 Tomcat 설치 필요
* Tomcat 버전/설정 차이로 환경 이슈 발생
* 배포 과정 복잡 (빌드 → 업로드 → 재시작)
* 개발/운영 환경 불일치
* 빠른 배포 어려움

->  한 줄 요약
**“애플리케이션이 서버에 종속됨”**

---

### 🚀 현재 방식 (Spring Boot + Embedded Tomcat)

Spring Boot는 **내장 톰캣(Embedded Tomcat)**을 포함하고 있다.

```bash
java -jar app.jar
```

이 한 줄로:

* 서버 실행
* HTTP 요청 처리
* 컨트롤러 호출

까지 전부 수행된다.

---

### 뭐가 달라졌나 (핵심 변화)

#### 1️⃣ WAS 설치가 필요 없음

* Tomcat을 따로 설치하지 않아도 됨
* JAR 안에 서버가 포함되어 있음

->  **“서버에 Java만 있으면 어디든 실행 가능”**

---

#### 2️⃣ 배포 방식 단순화

과거:

```text
WAR 빌드 → 서버 업로드 → Tomcat 배포 → 재시작
```

현재:

```text
JAR 빌드 → 서버 업로드 → java -jar 실행
```

->  배포 속도 + 안정성 ↑

---

#### 3️⃣ 환경 일관성 확보

* 개발 환경 = 운영 환경 동일
* "내 로컬에서는 되는데요?" 사라짐

->  장애 감소

---

#### 4️⃣ 애플리케이션 중심 구조

과거:

* 서버(Tomcat)가 중심
* 애플리케이션은 그 위에 올라감

현재:

* 애플리케이션이 서버를 포함

->  **“애플리케이션이 실행 주체가 됨”**

---

### 추가 이해 (왜 이런 구조가 가능해졌나)

내장 톰캣이 하는 일:

* HTTP 요청 수신
* 스레드 풀 관리 (동시 처리)
* 요청 → DispatcherServlet 전달
* 응답 생성

->  우리가 직접 할 필요 없음

---

### 순수 Java(ServerSocket) 방식의 한계

직접 서버를 만든다면:

```java
ServerSocket server = new ServerSocket(8080);
Socket socket = server.accept();
```

->  문제

* 동시 접속 처리 어려움 (멀티스레드 직접 구현)
* HTTP 파싱 직접 구현
* 라우팅(if문) 직접 처리
* 스레드/메모리 관리 필요

->  현실적으로 서비스 개발에 부적합

---

### 결론

* 과거: 서버 중심 (WAS 의존)
* 현재: 애플리케이션 중심 (내장 서버 포함)

->  핵심 변화

**“어디서든 동일하게 실행 가능한 구조”**

---

### 실무 관점 한 줄 정리

> Spring Boot는 내장 톰캣을 통해 WAS 의존성을 제거하고, JAR 기반 실행으로 배포 단순화와 환경 일관성을 확보했다.
