## 고성능 IO 처리

### 동기 vs 비동기

#### 동기 (Synchronous)
- 요청 → 응답 순서를 맞추며 처리하는 방식
- 하나의 작업이 끝나야 다음 작업 진행 가능

장점
- 흐름이 단순하고 이해하기 쉬움
- 디버깅이 쉬움

단점
- I/O 대기 시간 동안 스레드가 놀게 되어 비효율 발생
- 요청이 많아질수록 처리량 한계

적용 포인트
- 처리 순서가 중요한 경우
- 트래픽이 많지 않은 일반적인 웹 서비스

---

#### 비동기 (Asynchronous)
- 요청 후 결과를 나중에 받아 처리하는 방식
- 작업 완료를 기다리지 않고 다른 작업 수행 가능

장점
- I/O 대기 시간 활용 가능
- 높은 처리량 확보 가능

단점
- 코드 흐름이 복잡해짐
- 디버깅 난이도 상승

적용 포인트
- 외부 API 호출, 메시지 처리
- 응답 지연이 발생하는 작업이 많은 경우

---

### 플랫폼 스레드 vs 버추얼 스레드

#### 플랫폼 스레드
- OS 스레드 기반
- 생성 비용과 메모리 사용량이 큼

특징
- 안정적이고 검증된 방식
- 스레드 수가 많아지면 성능 저하 발생

---

#### 버추얼 스레드
- JVM에서 관리하는 경량 스레드
- 매우 많은 스레드를 생성 가능

장점
- 스레드 생성 비용 낮음
- 기존 동기 코드 그대로 사용 가능
- I/O 중심 작업에서 효율적

단점
- CPU 연산 작업에서는 큰 이점 없음
- 결국 스레드 기반이라 극단적인 트래픽에서는 한계 존재

핵심 포인트
- 버추얼 스레드는 비동기가 아니라
- "가벼운 스레드를 많이 사용할 수 있게 해주는 기술"

---

### 브로킹 vs 논 블로킹

#### Blocking
- 작업이 끝날 때까지 스레드가 대기하는 방식

특징
- 구현 단순
- 스레드 자원 낭비 발생 가능

---

#### Non-blocking
- 작업 완료를 기다리지 않고 다음 작업 수행

특징
- 적은 스레드로 많은 요청 처리 가능
- 이벤트 기반 구조와 함께 사용됨

---

핵심 정리
- Blocking / Non-blocking = 기다림 여부
- Sync / Async = 응답 방식

```bash
Blocking = 스레드가 기다리는 동안 아무것도 못함
Non-blocking = 스레드가 기다리지 않고 다른 요청 처리 가능
Sync = 결과를 받아야 다음 로직 실행
Async = 결과 없이도 다음 로직 실행
```

---

### 적용하는 기준

- 현재 시스템에 성능 문제가 있는가?
- 병목이 네트워크 I/O에서 발생하는가?
- 구조 변경이 가능한 상황인가?

위 조건 없이 기술 적용은 비효율적일 수 있음

---

### 반드시 적용해야 할까?

- 트래픽이 많지 않은 시스템에서는 불필요
- 단순한 서비스에 Non-blocking 구조를 적용하면 오히려 복잡도 증가
- 유지보수 난이도 상승 가능

핵심
- 문제 해결을 위한 기술 선택이 아니라
- 기술 적용 자체가 목적이 되면 안 된다

---

### 최종 정리

- 동기 → 단순하지만 대기 시간 발생
- 비동기 → 효율적이지만 복잡함
- 버추얼 스레드 → 동기 구조 유지하면서 성능 개선
- 논 블로킹 → 구조적으로 처리 방식 개선
